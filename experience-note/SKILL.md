# 经验小记

## 目的

这条笔记是留给未来自己的素材，不是事故台账。

两个用途：
- 回顾：半年后想起这活是什么、我当时怎么想通的、结果多少
- 展示：要讲给人听时，照着它铺成一段，不用再翻旧账

所以要留下的是三样：
- **思路**——怎么查、怎么判、怎么实现。下次遇到同类的，能直接搬。
- **成果**——量化后的前后对比。说给人听时有分量。
- **边界**——哪里没做、为什么不做。有这一样，前两样才可信。

## 动笔前：先问 AI 不知道的事

**只有用户知道的就三类，都要问：**

1. **背景**——这次是哪一类事、为什么值得记。它决定全文详略。
2. **弃掉的方案为什么弃**——上下文里没讨论过的那些。**问法要留一个空槽**：先列你看到的路，再问"还有哪条你考虑过但没列上"。只问"我猜的两条对不对"，会把讨论框在你列的方案里，用户心里那条多出来的选项就丢了。
3. **收工边界**——为什么这次只做到这儿，剩下的准备怎么办。写进「遗留」。顺带问一句：剩下的里面哪些不要现场、靠自己也能学（进「待展开」）。

第 3 类最容易漏：AI 只看见你做了什么，看不见你为什么不往下做。可能是跟同事商量过，可能是自己排过优先级，也可能根本没讨论、就是没时间——这些都不在上下文里。

没查的东西要分两堆，分法见「三栏各管一件事」；分不清就先问用户。

问法统一：**先猜，再让用户改**。

> 这次我理解是「清了团队一个长期小包袱」：框架支持热更新但没人接，容量服务一直被排除在外。
> 对的话我就按这个写；不对你说哪一类。
>
> 我列了三条路：全局广播、定时轮询、自建接口，还有哪条你考虑过但没列上？各自为什么弃？
>
> 这次只改容量服务，是因为其余服务要各自回归验证，先拿一个试？

常见类别（不限这些，但必须先说清是哪一类）：

- 啃下一个难题
- 性能优化，前后差一个量级
- 查清一个很难查的 bug
- 做了个工具或机制，把团队反复出现的麻烦一次解决掉
- 学到一条以前不懂的原理
- 清了团队一个长期的、没人愿意碰的小包袱

用户回一个字（对 / 改成 X）就够。三类一次问完，最多三条；某一类问不出东西时整行留空，不写"暂无"。

**背景和理由必须来自用户的回答。** AI 自己猜的、用户没确认过的背景或原因，不能进正文——猜错了整篇的详略都会错。

## 字段要求

| 字段 | 必须含 | 不合格 |
| --- | --- | --- |
| 问题 | 1 个可量化现象 | "系统很慢" ❌ |
| 背景 | 哪一类事 + 为什么值得记；用户确认过 | AI 自己猜、没跟用户对过的背景 ❌ |
| 难点 | 1–2 条卡点 + **1 条判断陷阱**；可以不是技术问题（团队旧习惯、没人碰的模块） | 拿细节凑满两条 ❌ |
| **调查** | **总思路**（多层排查才写）+ **排除顺序**：先排除什么、用什么看、依据是什么、所以是什么 | 操作流水账；只有命令、没有路线 ❌ |
| 方案取舍 | 至少 1 个被否决的方案 + 理由；选的那个也要给理由；不含机制和判据 | "综合考虑后决定" ❌ / 只写选了什么不写弃了什么 ❌ / 把技术原理当取舍写 ❌ |
| 修改 | 改了什么 + 关键参数为什么是这个值 + 怎么退 | "做了优化" ❌ |
| 结果 | 前后对比数字 | "明显改善" ❌ |
| 遗留 | 本次没解决的**范围**（多大一块）+ 为什么这次先不解决 + 会咬人的已知坑 | "还有优化空间" ❌ / 拿单个实例充当缺口 ❌ / "应该沉淀文档""应该推广" ❌ |
| 学到什么 | 会话里用户主动追问过、已经弄明白的机制或判据，能直接写出来 | 只写标题、挂"待查" ❌ |
| 待展开 | 不要现场也能学的通用问题，一行关键词 | 把"只能写个标题"的现场疑问塞进来 ❌ / 已经能写清却还挂在待展开 ❌ |

### 调查：先给路线，再给排除顺序

**这是最容易写错的一段。**

**两层都要有：**

- **总思路**（一行）：从哪一层查到哪一层。它回答"你怎么想起这么查的"。
- **每一步**：怀疑什么 → 用什么看 → 看出什么算判据 → 所以是什么。

只写排除顺序，读的人能看到你排了哪些嫌疑，看不到你为什么按这个顺序排。层数多、需要选顺序的问题（如 系统内存 → 服务内存 → 线程 → 火焰图），总思路就是最值钱的那一行；单点问题（一条 SQL 慢，加个索引）不写，写了是凑字。

```
✅ 排除顺序（要的）
总思路：整机 → 进程 → 线程 → 代码
1. 先排除 IO / 内存 / 内核 → wa=0、avail 16GB、sy 4.4%，锁定单个 java 进程
2. 再排除业务线程 → top -H 只见 5 个无名线程，转十六进制对照 jstack 的 nid，认出 GC 线程
3. 再确认根因 → jstat 显示老年代 175MB 用掉 167MB 回收不掉

❌ 操作顺序（不要）
1. top -bn1 / vmstat 排除磁盘 IO、内存、内核态
2. jps -l + ps args → PID 20767
3. top -H -p 20767 只给出 5 个线程号（20770/20771/...），20772 → 0x5124
4. jstat -gcutil → FGC 86,106 次
```

**区别：排除顺序讲"我怎么缩小范围的"，操作顺序讲"我跑了哪些命令"。总思路讲"我为什么按这个顺序缩"。**

面试官只会问前者。

### 判断陷阱是什么

**不是"技术难点"，是"当时最容易走错的方向"。**

它最值钱，因为它证明判断力：

> **判断陷阱**：227 正常、228 异常，差别只在 `-Xmx`（1512m vs 256m），容易先怀疑代码而不是先看部署参数。

**没有判断陷阱就整条省掉**，不写"暂无"，也不拿技术难点凑数。

## 不写什么

**写完先删一轮。删掉这些：**

| 删掉 | 理由 |
| --- | --- |
| 线程号、traceId、SQL 原文、日志全文 | 重新查一次就有，不影响叙事 |
| 精确到字节/毫秒的原始值 | 改成"14.8MB""约 58 秒"这类有叙事意义的量级 |
| 操作命令本身（`top -bn1`、`jstack`、`grep`） | 除非命令本身就是难点 |
| 项目规模、架构介绍 | 「背景」只写为什么值得记，不写系统科普 |

**留下的判据是「结论 + 为什么」，不是「原始输入」。**

自问一句：三个月后看到这个数字，能立刻给面试官讲出来吗？还是要重新查一遍当时的数据？

## 写短句

读起来费劲，多半是句子太长。规则取自阮一峰《中文技术文档的写作规范》，只留对小记有用的五条：

1. **一句一件事，30 字封顶。** 20 字内最好，超过 30 字就拆成两句。
2. **一条 bullet 不超过三行。** 一行装不下，说明里面塞了两件事，拆开。
3. **先结论，后依据。** 每条从"排除了什么""所以是什么"开头，再跟数据和手段。
4. **动词开头。** "先排除 IO"，不写"IO 已被排除"；"调堆到 1024m"，不写"堆大小的调整"。
5. **一个东西只用一种叫法。** 全篇统一叫"配置对象"，就别再换"配置类""配置实例"。

写完通读一遍：需要回头再读一次才懂的句子，拆短它。

## 三条硬规则

**① 锚点密度**

每个字段至少一个具体坐标，不写形容词。同样长度，锚点版信息量是 10 倍。

| 会忘 | 不会忘 |
| --- | --- |
| CPU 很高 | 整机 97–100%，持续 7 分钟 |
| 定位到慢查询 | `getFloorDevices` 320 次 × 5,975ms |
| 加索引后变快 | 198 秒 → 38 秒 |

**② 调查 / 方案取舍 / 修改三分**

三者不能合并，合并会吞掉决策理由。

- **调查**回答"问题在哪一层"：排除了什么、所以是什么
- **方案取舍**回答"为什么这么改"：选了哪条、弃了哪条，各自为什么
- **修改**回答"动了什么"：改了什么、参数为什么是这个值、怎么退

一句话：**调查里排的是嫌疑，方案取舍里比的是方案，修改里记的是落地。**

自测：有人问"为什么不换个办法"，这段能不能直接答上来？答不上就是没写清。

**③ 遗留 / 学到什么 / 待展开：三栏各管一件事**

**现场** = 那台机器当时的进程、参数、日志、堆。

三个字段都装"没完的事"，性质完全不同。一句话就能分开：

| 栏 | 装什么 | 一句话测 |
| --- | --- | --- |
| 学到什么 | 已经弄明白了的机制、判据、口诀 | 能直接写出来 |
| 待展开 | 以后还能学的通用问题 | 造环境、查文档、本地压测都能学，不依赖现场 |
| 遗留 | 本次没做完的活 | 答案只在现场，现场没了就没了 |

**遗留只装本次没做完的活，三样缺一条就别写：**

1. **范围**——还差多大一块："其余 17 个服务仍靠重启"。范围里的单个实例（某个服务漏引总线）是证据，并进同一条当括号，不单列。
2. **为什么这次先不解决**——回归范围、人力、风险。没这句，遗留读起来就像一张没做完的清单。这句问过用户没有，比写得漂不漂亮重要得多。
3. **会咬人的坑**——已知、这次没修、下次还会踩："删配置项不生效，停发某项要写 0"。

待验证的假设也进这栏，一行写完它的判据和时间："1024m 够不够撑每天 05:00 的全量同步，次日看"。它靠的是以后的数据，同样不是现在能写清的。

"解决了什么"由「结果」承担，这里只写缺口；文档、推广这类待办，等有了具体动作再进这栏。

**学到什么从哪来：看会话里用户主动追问过什么。** 主动问的才是他真在意的，也是这条小记最值钱的部分——它证明你不只修好了，还搞懂了。拿不准就问一句。

**三栏怎么分：**

- 已有事实、能直接写出来 → **学到什么**
- 造环境或查文档也能学 → **待展开**
- 答案只在现场 → **遗留**

**现场问题先拆成原理问题。** 同一件事常能拆成两半，别整条塞一个栏：

- 「cluster02 老年代 99%、15 小时只有 7 次 FGC」——现场缺口 → **遗留**
- 「老年代满了为什么不触发 Full GC」——原理问题 → **待展开**

拆得出来的一半进待展开，剩下那一半进遗留，简记一句并写明为什么不查。

例：

```
✅ 学到什么：没有 JVM 指标（up=0 断采 5 小时）时怎么定位 GC：先整机、再单进程、
            再单线程，用 jstack 的 nid 对照认出 GC 线程，再拿 jstat 看老年代回收不掉。
            —— 事实齐了，现在就能写出来。

✅ 待展开：老年代高水位为什么不触发 Full GC
        —— 跟这台机器无关，查文档、本地压测都能学。

✅ 遗留：cluster02 老年代 99% 却只有 7 次 FGC，没查清，现场已灭
        —— 答案在没了的现场里，只能记一句。

❌ 待展开：MQ 内存泄漏的增长曲线
        —— 要拉本次集群的历史内存数据，现场没了就查不了，该进「遗留」。
```

## 命令补课（可选）

**触发条件**（满足任一才加）：

- 用户明确问过某个命令是什么意思
- 本次用了非日常命令，且该命令的用法本身就是难点的一部分

**不默认加**，否则每条都附会让记录臃肿。最多 3 个命令。

**格式**：每个命令 3–4 行，讲清「它回答什么问题 → 关键参数 → 输出怎么读」。

例：

```
### top -H 的线程号怎么对应 jstack 的 nid

- `top -H` 给的是十进制线程号（如 20772）
- `jstack` 用十六进制表示：`nid=0x5124`
- 换算：`printf '0x%x\n' 20772` → `0x5124`，再到 jstack 输出里搜这个值
- 认出线程名后才知道是谁在烧 CPU：`GC task thread#0~3` 就是 ParallelGC 的回收线程
```

## 输出规则

- **先问再写。** 第一轮只出「动笔前」那两三个确认问题，用户答完才写正文。
- **正文只输出那一条 markdown**，不加"以下是记录：""希望对你有帮助"之类的任何解说，不加代码围栏包裹。用户要复制粘贴。
- 一次只输出一条。用户单独要模板时才只给模板。
- **标题不编号。** 直接写标题，不加 `N、` 之类的序号；标题 15 字以内，只留现象和关键根因，不堆过程细节。

## 取材清单

写之前先翻这四处：

| 要记的 | 去哪找 |
| --- | --- |
| **数字** | 监控面板、慢日志、`EXPLAIN`、测试结果、`git diff` |
| **排除了什么** | 试过但没用的方向（最容易忘，也最值钱） |
| **方案取舍** | 考虑过但放弃的方案，以及否决理由 |
| **参数取舍** | 为什么是 64 不是 256，为什么是 1024 不是 1512 |

## 自检

输出前逐条过：

- [ ] 背景、弃选理由、收工边界，都问过用户、用户确认了？
- [ ] 标题 15 字以内、不带序号，只写现象和关键根因？
- [ ] 「调查」是排除顺序，不是操作流水账？
- [ ] 「难点」里的卡点是真的卡点，不是为凑数写的细节？
- [ ] 删掉了线程号、traceId、SQL 原文这类可重查数据？
- [ ] 弄明白的写进了「学到什么」，能脱离现场自己再查的才留在「待展开」？
- [ ] 「遗留」写的是缺口范围，不是单个实例？
- [ ] 句子都在 30 字以内，没有需要回头再读一次的？
- [ ] 全文 1200 字以内？

## 示例

```
## 256m 堆引发 Full GC 死循环

**日期**：2026-10-22

**问题**：228 整机 CPU 73.5%（同集群 227 只有 14.4%）持续 4.7 小时，Full GC 86,836 次、停顿累计 17,038 秒。

**背景**：查一个线上故障：同集群两台机器，一台正常一台 CPU 打满，Prometheus 又断采 5 小时，只能上机手工查。属于「很难查的 bug」，顺手摸清了没监控时怎么定位 GC。

**难点**：
- Prometheus 恰好断采 5 小时，JVM 指标全无，只能上机手工查。
- `top -H` 的 COMMAND 列全显示 java，GC 线程和业务线程肉眼分不出。
- **判断陷阱**：227 正常、228 异常，差别只在 `-Xmx`（1512m vs 256m），容易先怀疑代码而不是先看部署参数。

**调查**：
总思路：先看整机资源排除硬件与内核，再把范围收到单进程，再收到单线程，最后才看代码与数据。
1. 先排除 IO / 内存 / 内核 → wa=0、avail 16GB、sy 4.4%，锁定单个 java 进程占 211%。
2. 再排除业务线程 → `top -H` 只见 5 个无名线程，转十六进制对照 `jstack` 的 `nid`，认出是 4 个 GC 线程 + VM Thread。
3. 再确认根因 → `jstat` 显示老年代 175MB 用掉 167MB、回收不掉；`jmap -histo` 显示 `[C]` 122MB / 55.7 万实例。
4. 再定位触发源 → 05:00 一次 U8 接口返回 14.8MB，mapper 用 `<foreach>` 把 35,868 行拼成单条 INSERT。
5. 再反证不是并发 → 两台同一 traceId 相差 58 秒 ≈ `ribbon.ReadTimeout: 60000`，是超时换台重试。

**方案取舍**：怎么让这次同步跑完？
- 选「调堆 256m → 1024m」：1 行启动参数、零代码改动、10 分钟见效。
- 弃「改分批插入」：U8 同步每天 05:00 只触发一次、只有一个接口，3~5 人日换不来收益。

**修改**：
```
