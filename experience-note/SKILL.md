# 经验小记

## 目的

记录问题的原始事实，不展开细节。三个约束同时成立：

- **快写**：一条不超过 800 字
- **可重建**：几个月后凭它写出完整故事
- **可用于求职**：留下"怎么想"和"放弃了什么"，不只记结果

**它是索引，不是全文。** 现在记的是"以后展开时用得上的锚点"，不是把调查过程完整复述一遍。

## 模板

```
## N、<一句话标题：现象 + 根因>

**日期**：YYYY-MM-DD（跨天写范围）

**问题**：<看到了什么，含 1 个数字>

**难点**：
- <技术难点 1>
- <技术难点 2>
- **判断陷阱**：<当时最容易走错的方向>

**调查**：按排除顺序写，不按操作顺序。
1. 先排除 <A> → <依据>，所以是 <B>
2. 再排除 <C> → <依据>，所以是 <D>
3. 再确认 <根因> → <判据>

**判断**：<方案岔路口>
- 选 <A>：<理由>
- 弃 <B>：<理由>

**修改**：
1. <改了什么>
2. ...

回滚：<怎么退>

**结果**：<前> → <后>；<前> → <后>

**遗留**：
- <风险、未解决的问题>
- <待验证的假设>

**待展开**：
- <草稿里已提到、但写得太粗的段落>
```

## 字段要求

| 字段 | 必须含 | 不合格 |
| --- | --- | --- |
| 问题 | 1 个可量化现象 | "系统很慢" ❌ |
| 难点 | 2 条技术难点 + **1 条判断陷阱** | 三条都是技术难点 ❌ |
| **调查** | **排除顺序**：先排除什么、依据是什么、所以是什么 | 操作流水账 ❌ |
| 判断 | 至少 1 个被否决的选项 + 理由 | "综合考虑后决定" ❌ |
| 修改 | 改了什么 + 关键参数为什么是这个值 + 怎么退 | "做了优化" ❌ |
| 结果 | 前后对比数字 | "明显改善" ❌ |
| 遗留 | 风险 + 未解决的问题 + 待验证假设 | "还有优化空间" ❌ |
| 待展开 | 草稿里已提到的点，缺的只是篇幅 | 只有现象、没查原因的待办 ❌ |

### 调查：排除顺序 vs 操作顺序

**这是最容易写错的一段。**

```
✅ 排除顺序（要的）
1. 先排除 IO / 内存 / 内核 → wa=0、avail 16GB、sy 4.4%，锁定单个 java 进程
2. 再排除业务线程 → top -H 只见 5 个无名线程，转十六进制对照 jstack 的 nid，认出 GC 线程
3. 再确认根因 → jstat 显示老年代 175MB 用掉 167MB 回收不掉

❌ 操作顺序（不要）
1. top -bn1 / vmstat 排除磁盘 IO、内存、内核态
2. jps -l + ps args → PID 20767
3. top -H -p 20767 只给出 5 个线程号（20770/20771/...），20772 → 0x5124
4. jstat -gcutil → FGC 86,106 次
```

**区别：排除顺序讲"我怎么缩小范围的"，操作顺序讲"我跑了哪些命令"。**

面试官只会问前者。

### 判断陷阱是什么

**不是"技术难点"，是"当时最容易走错的方向"。**

它最值钱，因为它证明判断力：

> **判断陷阱**：227 正常、228 异常，差别只在 `-Xmx`（1512m vs 256m），容易先怀疑代码而不是先看部署参数。

**如果没有判断陷阱，这条就写"暂无"——不要用技术难点凑数。**

## 不写什么

**写完先删一轮。删掉这些：**

| 删掉 | 理由 |
| --- | --- |
| 线程号、traceId、SQL 原文、日志全文 | 重新查一次就有，不影响叙事 |
| 精确到字节/毫秒的原始值 | 改成"14.8MB""约 58 秒"这类有叙事意义的量级 |
| 操作命令本身（`top -bn1`、`jstack`、`grep`） | 除非命令本身就是难点 |
| 系统背景（项目多大、架构如何） | 除非它是难点的一部分 |

**留下的判据是「结论 + 为什么」，不是「原始输入」。**

自问一句：三个月后看到这个数字，能立刻给面试官讲出来吗？还是要重新查一遍当时的数据？

## 三条硬规则

**① 锚点密度**

每个字段至少一个具体坐标，不写形容词。同样长度，锚点版信息量是 10 倍。

| 会忘 | 不会忘 |
| --- | --- |
| CPU 很高 | 整机 97–100%，持续 7 分钟 |
| 定位到慢查询 | `getFloorDevices` 320 次 × 5,975ms |
| 加索引后变快 | 198 秒 → 38 秒 |

**② 调查 / 判断 / 修改三分**

三者不能合并，合并会吞掉决策理由。

- **调查**回答"是什么"：排除了什么、所以是什么
- **判断**回答"怎么办"：方案 A 还是 B，弃掉的那个为什么弃
- **修改**回答"怎么落地"：改了什么、参数为什么是这个值、怎么退

一句话：**调查里排的是嫌疑，判断里选的是方案。**

**③ 遗留与待展开必须分清**

两个字段都装"没完的事"，但性质相反：

| | 遗留 | 待展开 |
| --- | --- | --- |
| 是什么 | 风险、未解决的问题 | 草稿里写得太粗、值得写细的段落 |
| 需要现场吗 | 需要，但现场已经没了 | 不需要，已有事实就够 |
| 后续动作 | 只能记录状态、接受 | 把一句话写成一节 |
| 会过期吗 | 会（验证完就删，或永久接受） | 不会（事实永远有效） |

**判断问句：**

- 这件事需要新证据才能推进吗？→ 是 → **遗留**
- 这件事只用记录里已有的事实就能写细吗？→ 是 → **待展开**

**展开的内容一般都来自笔记里已经提到的点**。笔记是最初的草稿，写得很粗；展开时是把草稿里不充分的地方写充分，而不是去解决草稿里没解决的问题——后续整理笔记时，现场已经没了，也解决不了。

例：

```
✅ 待展开：这次 Prometheus 断采，只能手工定位 JVM
          —— 难点里提了一句、调查里写了三步，事实齐了，
             展开能写成"没有监控时怎么查 GC"一整节。

✅ 遗留：227 有 1131 线程、228 只有 228 线程，5 倍差异没查
        —— 只有现象，要查需要现场（线程还在的时候），现在没了。
```

## 命令补课（可选）

**触发条件**（满足任一才加）：

- 用户明确问过某个命令是什么意思
- 本次用了非日常命令，且该命令的用法本身就是难点的一部分

**不默认加**，否则每条都附会让记录臃肿。最多 3 个命令。

**格式**：每个命令 3–4 行，讲清「它回答什么问题 → 关键参数 → 输出怎么读」。

例：

```
### top -H 的线程号怎么对应 jstack 的 nid

- `top -H` 给的是十进制线程号（如 20772）
- `jstack` 用十六进制表示：`nid=0x5124`
- 换算：`printf '0x%x\n' 20772` → `0x5124`，再到 jstack 输出里搜这个值
- 认出线程名后才知道是谁在烧 CPU：`GC task thread#0~3` 就是 ParallelGC 的回收线程
```

## 输出规则

- **只输出那一条 markdown**，不加"以下是记录：""希望对你有帮助"之类的任何解说，不加代码围栏包裹。用户要复制粘贴。
- 一次只输出一条。用户单独要模板时才只给模板。
- **编号不猜。** 用户没给时输出 `## N、` 原样保留，由用户自己填。

## 取材清单

写之前先翻这四处：

| 要记的 | 去哪找 |
| --- | --- |
| **数字** | 监控面板、慢日志、`EXPLAIN`、测试结果、`git diff` |
| **排除了什么** | 试过但没用的方向（最容易忘，也最值钱） |
| **岔路口** | 考虑过但放弃的方案，以及否决理由 |
| **参数取舍** | 为什么是 64 不是 256，为什么是 1024 不是 1512 |

## 自检

输出前逐条过：

- [ ] 「调查」是排除顺序，不是操作流水账？
- [ ] 「难点」里有一条判断陷阱？
- [ ] 删掉了线程号、traceId、SQL 原文这类可重查数据？
- [ ] 「待展开」里的每一条，都是记录里已经写过的点，而不是新冒出来的待办？
- [ ] 需要新证据才能推进的，放在了「遗留」而不是「待展开」？
- [ ] 全文 800 字以内？

## 示例

```
## 23、预发布 228 整机 CPU 73%，根因是 256m 堆跑 U8 全量同步触发 Full GC 死循环

**日期**：2026-10-22

**问题**：228 整机 CPU 73.5%（同集群 227 只有 14.4%）持续 4.7 小时，Full GC 86,836 次、停顿累计 17,038 秒。

**难点**：
- Prometheus 恰好断采 5 小时，JVM 指标全无，只能上机手工查。
- `top -H` 的 COMMAND 列全显示 java，GC 线程和业务线程肉眼分不出。
- **判断陷阱**：227 正常、228 异常，差别只在 `-Xmx`（1512m vs 256m），容易先怀疑代码而不是先看部署参数。

**调查**：
1. 先排除 IO / 内存 / 内核 → wa=0、avail 16GB、sy 4.4%，锁定单个 java 进程占 211%。
2. 再排除业务线程 → `top -H` 只见 5 个无名线程，转十六进制对照 `jstack` 的 `nid`，认出是 4 个 GC 线程 + VM Thread。
3. 再确认根因 → `jstat` 显示老年代 175MB 用掉 167MB、回收不掉；`jmap -histo` 显示 `[C]` 122MB / 55.7 万实例。
4. 再定位触发源 → 05:00 一次 U8 接口返回 14.8MB，mapper 用 `<foreach>` 把 35,868 行拼成单条 INSERT。
5. 再反证不是并发 → 两台同一 traceId 相差 58 秒 ≈ `ribbon.ReadTimeout: 60000`，是超时换台重试。

**判断**：怎么让这次同步跑完？
- 选「调堆 256m → 1024m」：1 行启动参数、零代码改动、10 分钟见效。
- 弃「改分批插入」：U8 同步每天 05:00 只触发一次、只有一个接口，3~5 人日换不来收益。

**修改**：
1. `-Xmx256m -Xms256m` → `-Xmx1024m -Xms512m`（他人执行）。
2. 没照抄 227 的 1512m，先取 1024m 试探。

回滚：改回 `-Xmx256m` 重启，无代码变更。

**结果**：CPU 73.5% → 12.1%，load 3.30 → 1.21；FGC 86,836 次 / 17,038 秒 → 4 次 / 0.4 秒；Prometheus 断采 5 小时后恢复。

**遗留**：
- GET 承载写操作 + 读超时换台重试，同一份数据会在两台各跑一遍；业务冷门，风险接受留档。
- 1024m 是否够撑每天 05:00 的全量同步，待次日验证。
- 227 有 1131 线程、228 只有 228 线程，5 倍差异没查。

**待展开**：
- 没有 JVM 指标（up=0 断采 5 小时）时，手工定位 GC 死循环的完整路径。
```
