# 经验小记

## 目的

记录问题的原始事实，不展开细节。三个约束同时成立：

- **快写**：一条不超过 30 行
- **可重建**：几个月后凭它写出完整故事
- **可用于求职**：留下"怎么想"和"放弃了什么"，不只记结果

它是压缩器，不是扩写器。

## 模板

```
## N、<一句话标题：现象 + 根因>

**日期**：YYYY-MM-DD（跨天写范围）

**问题**：<看到了什么，含 1 个数字>

**难点**：
- <为什么不好办 1>
- <为什么不好办 2>
- <为什么不好办 3>

**调查**：
1. <方法> → <排除了什么 / 定位到什么>
2. ...

**判断**：<方案岔路口>
- 选 <A>：<理由>
- 弃 <B>：<理由>

**修改**：
1. <改了什么>
2. ...

回滚：<怎么退>

**结果**：<前> → <后>；<前> → <后>

**未解**：<一句边界：它解决了什么，没解决什么>

**钩子**：
- <后续可展开的点>
```

## 字段必含

| 字段 | 必须含 | 不合格 |
| --- | --- | --- |
| 问题 | 1 个可量化现象 | "系统很慢" ❌ |
| 难点 | 每条一个具体原因 | "比较复杂" ❌ |
| 调查 | 排除了什么 + 定位到什么 | 只写"分析了性能" ❌ |
| 判断 | 至少 1 个被否决的选项 + 理由 | "综合考虑后决定" ❌ |
| 修改 | 改了什么 + 怎么退 | "做了优化" ❌ |
| 结果 | 前后对比数字 | "明显改善" ❌ |
| 未解 | 1 条具体边界 | "还有优化空间" ❌ |
| 钩子 | 每条一句，最多 3 条 | 写成小作文 ❌ |

## 四条硬规则

**① 锚点密度**

每个字段至少一个具体坐标，不写形容词。同样长度，锚点版信息量是 10 倍。

| 会忘 | 不会忘 |
| --- | --- |
| CPU 很高 | 整机 97–100%，持续 7 分钟 |
| 定位到慢查询 | `getFloorDevices` 320 次 × 5,975ms |
| 加索引后变快 | 198 秒 → 38 秒 |

**② 调查 / 判断 / 修改三分**

三者不能合并，合并会吞掉决策理由。

- **调查**回答"是什么"：试了什么、排除了什么、定位到什么
- **判断**回答"怎么办"：方案 A 还是 B，弃掉的那个为什么弃
- **修改**回答"怎么落地"：改了什么、关键参数为什么是这个值、怎么退

一句话区分：**调查里排的是嫌疑，判断里选的是方案。**

**③ 钩子必须留**

钩子是给未来的自己留的展开线索，标记"还有哪些料没写"。没有钩子，半年后只能重写。

钩子记三类：容易被追问的取舍、当时没想通的矛盾、这次没验证的假设。

**④ 纯输出 markdown**

只输出那一条 markdown，不加"以下是记录：""希望对你有帮助"之类的任何解说，不加代码围栏包裹。用户要复制粘贴。

一次只输出一条。用户单独要模板时才只给模板。

## 取材清单

写之前先翻这四处，想不起来的细节都在这儿：

| 要记的 | 去哪找 |
| --- | --- |
| **数字** | 监控面板、慢日志、`EXPLAIN` 输出、测试结果、`git diff` |
| **排除了什么** | 试过但没用的方向（最容易忘，也最值钱） |
| **岔路口** | 考虑过但放弃的方案，以及当初否决它的理由 |
| **参数取舍** | 为什么是 64 不是 256，为什么是 8 不是 16 |

**第三、四项是面试唯一会追问的东西。**

## 编号

skill 不猜编号。用户没给时，输出 `## N、` 原样保留，由用户自己填。

## 示例（压缩版）

结构完整，每条只留一行。实际记录可以更详细。

```
## 23、公共权限楼层初始化整机卡死，根因是两条全表扫 SQL

**日期**：2026-10-20 ~ 2026-10-22

**问题**：预发布整机 CPU 97–100% 持续 7 分钟，接口 15–32 秒，load1 冲到 63.26。

**难点**：
- 直觉会怀疑 Java，但拆开看应用只占 0.53 核。
- 慢队列积压 25k 条像故障，实际是设计预期（Thread.sleep 700）。
- 两阶段混淆：初始化期 CPU 满、慢队列期 CPU 低，是两个问题。

**调查**：
1. 拆进程 CPU → 应用 0.53 核 vs 整机 3.77 核，**排除 Java**。
2. 逐条证伪磁盘 IO 8%、锁等待 0、连接 150/214，**排除资源嫌疑**。
3. digest 表 + SUM_NO_INDEX_USED → 三条 SQL 100% 无索引，**锁定全表扫**。

**判断**：MySQL 占 3.2 核，怎么治？
- 选「加索引」：1 条 DDL、零代码改动、实测 14.5×。
- 弃「改批量」：跨 3 层调用、1,157 张分表、改消息契约、3–5 人日。YAGNI。

**修改**：
1. idx_elevator_device_unique(64) —— 前缀 64 是撞了 767 字节限制后的取舍。
2. 换项目 00005412 端到端验证（原项目已 COMPLETED 无法重跑）。

回滚：DROP INDEX，无代码变更，随时可退。

**结果**：初始化 198 秒 → 38 秒；慢 SQL 320 次 → 0 次；单条最大 14,006ms → 145ms。

**未解**：索引只让每次更快，没减少调用次数（getPullData 仍执行 8,185 次）。

**钩子**：
- 767 字节限制的成因，以及为什么没选改字段类型。
- load1Ratio 0.50 反向限制扩容，与"CPU 高说明要更多消费者"矛盾。
```
